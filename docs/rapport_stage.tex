\chapter*{Résumé}
\addcontentsline{toc}{chapter}{Résumé}
Ce stage d'initiation porte sur la conception et la réalisation d'une mini-API REST de gestion d'assurance chez Vermeg. L'objectif est d'exposer de manière sûre, cohérente et documentée les opérations de gestion d'un portefeuille d'assurance élémentaire : clients, contrats, sinistres et gestion des utilisateurs.
Le système est implémenté en Java~17 / Spring Boot~3.5 avec PostgreSQL~16, sécurisé par JWT, documenté par OpenAPI/Swagger~UI, conteneurisé via Docker Compose, et consommé par un client Angular~17+. Des règles métier fortes sont centralisées côté serveur : unicité CIN, âge minimal 18~ans, soft-delete des clients, validation des périodes contractuelles, interdiction de déclaration de sinistre hors contrat ACTIF ou hors période de couverture, upload optionnel de justificatifs.
Le rapport présente l'analyse du besoin, la conception en couches, la réalisation backend et frontend, la stratégie de vérification, les difficultés rencontrées et les perspectives d'amélioration, notamment le durcissement de la gestion d'erreurs et l'introduction de migrations versionnées.
\noindent\textbf{Mots-clés :} API REST, Spring Boot, PostgreSQL, JWT, Angular, assurance, Docker, OpenAPI.

\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
This internship report presents the design and implementation of a REST mini-API for insurance management at Vermeg. The goal is to expose secure, consistent and documented operations for managing basic insurance portfolios: clients, contracts, claims and user management.
The system is built with Java~17 / Spring Boot~3.5, PostgreSQL~16, secured with JWT, documented via OpenAPI/Swagger~UI, containerized with Docker Compose, and consumed by an Angular~17+ client. Strong business rules are enforced server-side: unique CIN, minimum age~18, soft-delete for clients, contractual period validation, claim prohibition outside ACTIVE contracts or coverage period, optional document upload.
The report details needs analysis, layered design, backend and frontend implementation, verification strategy, encountered difficulties and improvement perspectives.
\noindent\textbf{Keywords:} REST API, Spring Boot, PostgreSQL, JWT, Angular, insurance, Docker, OpenAPI.

\chapter{Contexte et analyse du besoin}
\section{Contexte métier}
Un \textbf{client} est une personne physique identifiée par CIN unique, avec contrainte d'âge légal $\geq 18$~ans. Un \textbf{contrat} lie un client à une garantie : numéro de police unique généré par le serveur, type (AUTO, HOME, HEALTH, LIFE), période de validité, montants, statut (ACTIVE, EXPIRED, TERMINATED). Un \textbf{sinistre} est un événement dommageable déclaré au titre d'un contrat : numéro unique, description, date de survenance, date de déclaration (serveur), montants, statut (SUBMITTED, PROCESSING, ACCEPTED, REJECTED) et chemin vers document justificatif optionnel. Un \textbf{utilisateur} porte un username unique, un email unique, firstName/lastName, et un rôle ADMIN ou AGENT.
Invariants principaux :
\begin{itemize}
\item Un sinistre implique un contrat ACTIF existant et une date dans la période de couverture ;
\item Un client ne peut être supprimé physiquement (soft-delete via champ \texttt{active}) ;
\item Un utilisateur ADMIN gère les employés.
\end{itemize}

\section{Architecture applicative en couches}
Paquetages : \texttt{domain}, \texttt{dto} (records), \texttt{mapper}, \texttt{repository}, \texttt{service}, \texttt{controller}, \texttt{security}, \texttt{config}, \texttt{exception}. DTO distincts des entités : \texttt{ClientCreateDto} exige CIN, \texttt{ClientUpdateDto} ne l'exige pas. \texttt{RegisterRequest} exige firstName/lastName/email conformément à la nouvelle entité User.
\section{Conception de la sécurité}
JWT RFC~7519 \cite{jwt2015}. Login $\rightarrow$ token signé HMAC 24~h. Filtre \texttt{JwtAuthFilter} placé BEFORE \texttt{UsernamePasswordAuthenticationFilter}. L'autorisation par rôle est \textbf{effective au niveau du SecurityFilterChain} :
\begin{lstlisting}[language=Java, caption=SecurityConfig --- autorisation par rôle effective, label=lst:sec]
.authorizeHttpRequests(auth -> auth
  .requestMatchers("/api/auth/**").permitAll()
  .requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll()
  .requestMatchers("/api/users/**").hasRole("ADMIN")
  .requestMatchers(
    "/api/clients/**",
    "/api/contracts/**",
    "/api/claims/**")
    .hasAnyRole("ADMIN", "AGENT")
  .anyRequest().authenticated()
)
.sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
\end{lstlisting}
Les annotations \texttt{@PreAuthorize} restent en double défense, mais la protection principale est assurée au niveau HTTP. Mots de passe BCrypt, CSRF désactivé (justifié : API sans cookie) \cite{springsec}.
\section{Conception de l'API REST}
REST : ressources plurielles, verbes HTTP sémantiques, codes RFC~9110 \cite{http2022}. Les sinistres sont exposés en sous-ressource du contrat. Génération serveur : policyNumber, claimNumber, createdAt, declarationDate, statut initial. La création d'un sinistre utilise \texttt{multipart/form-data} pour supporter l'upload de fichier.
\section{Environnement conteneurisé}

\section{Persistance et règles métier}
\begin{lstlisting}[language=Java, caption=ClientService --- CIN unique + âge >=18 + soft-delete]
@Transactional
public ClientResponseDto createClient(ClientCreateDto dto) {
  if (clientRepository.existsByCin(dto.cin()))
    throw new BusinessRuleException("CIN deja existant");
  if (dto.birthDate().isAfter(LocalDate.now().minusYears(18)))
    throw new BusinessRuleException("Client >= 18 ans requis");
  Client c = ClientMapper.toEntity(dto);
  c.setCreatedAt(LocalDate.now());
  c.setActive(true);
  return ClientMapper.toDto(clientRepository.save(c));
}
public List<ClientResponseDto> listClients() {
  return clientRepository.findByActiveTrue()
    .stream()
    .map(ClientMapper::toDto)
    .toList();
}
public void deleteClient(Long id) {
  Client c = clientRepository.findById(id)
    .orElseThrow(() -> new ResourceNotFoundException("Client introuvable"));
  c.setActive(false); // soft-delete
  clientRepository.save(c);
}

@Transactional
public ClaimResponseDto createClaim(
  Long contractId, ClaimCreateDto dto, MultipartFile file) {
  Contract contract = contractRepository.findById(contractId)
    .orElseThrow(() -> new ResourceNotFoundException("Contrat introuvable"));
  if (contract.getStatus() != ContractStatus.ACTIVE)
    throw new BusinessRuleException("Contrat non ACTIVE");
  if (dto.claimDate().isBefore(contract.getStartDate())
      || dto.claimDate().isAfter(contract.getEndDate()))
    throw new BusinessRuleException("Claim date hors periode");
  Claim claim = new Claim();
  claim.setContract(contract);
  claim.setDescription(dto.description());
  claim.setClaimDate(dto.claimDate());
  claim.setDeclarationDate(LocalDate.now());
  claim.setEstimatedAmount(dto.estimatedAmount());
  claim.setReimbursedAmount(BigDecimal.ZERO);
  claim.setStatus(ClaimStatus.SUBMITTED);
  claim.setClaimNumber(
    "CL-" + Year.now() + "-" + (System.currentTimeMillis() % 100000));
  if (file != null && !file.isEmpty()) {
    String unique = UUID.randomUUID() + ext(file);
    Path dest = rootLocation.resolve(unique);
    Files.copy(file.getInputStream(), dest);
    claim.setDocumentPath(dest.toString());
  }
  return ClaimMapper.toDto(claimRepository.save(claim));
}
\end{lstlisting}

\section{Regard critique et limites}
\textbf{Correction depuis la première version :} l'autorisation par rôle est désormais effective au niveau HTTP (\texttt{hasRole}/\texttt{hasAnyRole}). Dans la première version, les annotations \texttt{@PreAuthorize} étaient inopérantes faute de \texttt{@EnableMethodSecurity} --- défaut corrigé. Le frontend est passé de maquette partielle à client complet avec administration des employés.
\textbf{Limites restantes :}
\begin{itemize}
\item Gestion d'erreurs trop uniforme : le handler renvoie souvent 400 au lieu de 404/409/422/403 selon le type ; format RFC~9457 \cite{rfc9457} non appliqué.
\item Secret JWT en clair dans \texttt{application.yaml}, devrait être une variable d'environnement.
\item Schéma géré par \texttt{hibernate.ddl-auto=update}, non versionné, non rollbackable.
\item JWT peu défensif : pas de claim rôle, durée 24~h longue, pas de refresh/révocation, \texttt{TokenExpiredException} non capturée dans le filtre (500 au lieu de 401).
\item Image Docker exécutée en root, pas de limites de ressources, pas de cache Maven, tests ignorés dans le build.
\item Pas de CI, pas de pagination/filtrage, README désaligné.
\item Stockage local \texttt{uploads/} non persistant hors volume, pas de limite de taille, pas de validation du type MIME.
\end{itemize}

\chapter{Conclusion}
Ce stage d'un mois chez Vermeg a permis de réaliser une mini-API REST assurance opérationnelle sur le périmètre demandé et élargi. Le service expose des clients avec règles CIN/âge/soft-delete, des contrats avec numérotation serveur, des sinistres avec validation de période et de statut ainsi qu'upload de justificatif, et des utilisateurs avec rôles ADMIN/AGENT effectifs au niveau HTTP Security et guards Angular. La base PostgreSQL, les JWT 24~h, la validation des entrées, les règles métier centralisées, la documentation OpenAPI interactive, l'environnement Docker Compose reproductible et le client Angular complet constituent le livrable final.
Sur le plan technique, ce stage a permis de découvrir l'écosystème Spring Boot, JPA, Spring Security, Docker et Angular avec guards. L'architecture en couches, les DTO et les règles centralisées côté serveur sont désormais des réflexes acquis.
Sur le plan critique, le travail comporte des faiblesses documentées : gestion d'erreurs uniforme, secret non externalisé, couverture de tests faible, conteneurisation dev-only, stockage de fichiers simple. Le point positif majeur par rapport au rapport initial est que l'autorisation par rôle est désormais effective, contrairement à la première version où \texttt{@PreAuthorize} était inopérant sans \texttt{@EnableMethodSecurity} --- défaut corrigé par la configuration HTTP Security. Ce stage a offert un premier aperçu d'un éditeur logiciel financier où la correction, la traçabilité et la lisibilité comptent autant que les fonctionnalités visibles, une exigence à conserver pour la suite du cursus.
