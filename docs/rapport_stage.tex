\chapter*{Résumé}
\addcontentsline{toc}{chapter}{Résumé}
Ce stage d'initiation porte sur la conception et la réalisation d'une mini-API REST de gestion d'assurance chez Vermeg. L'objectif est d'exposer de manière sûre, cohérente et documentée les opérations de gestion d'un portefeuille d'assurance élémentaire : clients, contrats, sinistres et gestion des utilisateurs.

Le système est implémenté en Java 17 / Spring Boot 3.5 avec PostgreSQL 16, sécurisé par JWT, documenté par OpenAPI/Swagger UI, conteneurisé via Docker Compose, et consommé par un client Angular 17+. Des règles métier fortes sont centralisées côté serveur : unicité CIN, âge minimal 18 ans, soft-delete des clients, validation des périodes contractuelles, interdiction de déclaration de sinistre hors contrat ACTIF ou hors période de couverture, upload optionnel de justificatifs.

Le rapport présente l'analyse du besoin, la conception en couches, la réalisation backend et frontend, la stratégie de vérification, les difficultés rencontrées et les perspectives d'amélioration, notamment le durcissement de la gestion d'erreurs et l'introduction de migrations versionnées.

\noindent\textbf{Mots-clés :} API REST, Spring Boot, PostgreSQL, JWT, Angular, assurance, Docker, OpenAPI.

\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
This internship report presents the design and implementation of a REST mini-API for insurance management at Vermeg. The goal is to expose secure, consistent and documented operations for managing basic insurance portfolios: clients, contracts, claims and user management.

The system is built with Java 17 / Spring Boot 3.5, PostgreSQL 16, secured with JWT, documented via OpenAPI/Swagger UI, containerized with Docker Compose, and consumed by an Angular 17+ client. Strong business rules are enforced server-side: unique CIN, minimum age 18, soft-delete for clients, contractual period validation, claim prohibition outside ACTIVE contracts or coverage period, optional document upload.

The report details needs analysis, layered design, backend and frontend implementation, verification strategy, encountered difficulties and improvement perspectives.

\noindent\textbf{Keywords:} REST API, Spring Boot, PostgreSQL, JWT, Angular, insurance, Docker, OpenAPI.

\chapter{Introduction}
Le cursus de licence en informatique de l'ISIMG prévoit un stage d'initiation de quatre semaines continues afin de découvrir l'organisation d'une entreprise du secteur et de mettre en pratique les acquis de première année.

J'ai effectué ce stage du 1er au 31 juillet 2026 chez Vermeg, éditeur de solutions logicielles pour les services financiers et l'assurance, sous l'encadrement de Mme Faten Kardous, \textit{Lead Developer} Insurance Market Operations.

Le sujet confié porte sur la réalisation d'une \textbf{mini-API REST de gestion d'assurance} : construire à partir de zéro un service web gérant les objets élémentaires d'un système assurantiel — clients, contrats, sinistres et utilisateurs — en respectant les pratiques de l'entreprise.

Problématique : \textit{comment exposer, de manière sûre, cohérente, documentée et reproductible, les opérations de gestion d'un portefeuille d'assurance élémentaire, tout en garantissant le respect des règles qui lient un sinistre à son contrat et un contrat à son client ?}

Objectifs opérationnels : modéliser le domaine sous forme d'entités persistantes ; exposer une API REST complète ; faire respecter les règles métier par le serveur ; sécuriser les accès par jeton avec rôles ADMIN/AGENT effectifs ; permettre l'upload de justificatifs de sinistres ; documenter l'interface de manière interactive ; rendre l'environnement d'exécution reproductible ; valider la consommation par un client Angular.

Le rapport suit six chapitres : présentation de l'entreprise, analyse du besoin, conception, réalisation, vérification et regard critique, puis bilan.

\chapter{Contexte et analyse du besoin}

\section{Contexte métier}
Un client est une personne physique identifiée par CIN unique, avec contrainte d'âge légal >=18 ans. Un contrat lie client à une garantie : numéro de police unique généré serveur, type (AUTO, HOME, HEALTH, LIFE), période validité, montants, statut (ACTIVE, EXPIRED, TERMINATED). Un sinistre est un événement dommageable déclaré au titre d'un contrat : numéro unique, description, date survenance, date déclaration serveur, montants, statut (SUBMITTED, PROCESSING, ACCEPTED, REJECTED) et chemin vers document justificatif optionnel. Un utilisateur porte username unique, email unique, firstName/lastName, rôle ADMIN ou AGENT.

Invariants : sinistre implique contrat ACTIF existant et date dans période de couverture ; client ne peut être supprimé physiquement (soft-delete par champ \texttt{active}) ; utilisateur ADMIN gère employés.

\section{Conception de la sécurité - version corrigée effective}
JWT RFC7519 \cite{jwt2015}. Login -> token signé HMAC 24h. Filtre JwtAuthFilter BEFORE UsernamePasswordAuthenticationFilter.

Correction majeure depuis rapport initial : autorisation par rôle désormais \textbf{effective} au niveau SecurityFilterChain, pas seulement @PreAuthorize :

\begin{lstlisting}[language=Java, caption=SecurityConfig - autorisation par rôle effective, label=lst:sec]
.authorizeHttpRequests(auth -> auth
  .requestMatchers("/api/auth/**").permitAll()
  .requestMatchers("/swagger-ui/**","/v3/api-docs/**").permitAll()
  .requestMatchers("/api/users/**").hasRole("ADMIN")
  .requestMatchers("/api/clients/**","/api/contracts/**","/api/claims/**")
     .hasAnyRole("ADMIN","AGENT")
  .anyRequest().authenticated()
)
.sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
\end{lstlisting}

Les @PreAuthorize restent en double défense mais la protection principale est HTTP. BCrypt, CSRF désactivé justifié API sans cookie \cite{springsec}.

\section{Persistance et règles métier nouvelles}

ClientService final :

\begin{lstlisting}[language=Java, caption=ClientService - CIN unique, age >=18, soft-delete]
@Transactional
public ClientResponseDto createClient(ClientCreateDto dto){
  if(clientRepository.existsByCin(dto.cin()))
    throw new BusinessRuleException("CIN deja existant");
  if(dto.birthDate().isAfter(LocalDate.now().minusYears(18)))
    throw new BusinessRuleException("Client >=18 ans requis");
  Client c = ClientMapper.toEntity(dto);
  c.setCreatedAt(LocalDate.now());
  c.setActive(true);
  return ClientMapper.toDto(clientRepository.save(c));
}
public List<ClientResponseDto> listClients(){
  return clientRepository.findByActiveTrue().stream().map(ClientMapper::toDto).toList();
}
public void deleteClient(Long id){
  Client c = clientRepository.findById(id).orElseThrow(...);
  c.setActive(false); // soft-delete
  clientRepository.save(c);
}
\end{lstlisting}

public ClaimResponseDto createClaim(Long contractId, ClaimCreateDto dto, MultipartFile file){
  Contract contract = contractRepository.findById(contractId).orElseThrow(...);
  if(contract.getStatus()!=ACTIVE) throw new BusinessRuleException("Contract not ACTIVE");
  if(dto.claimDate().isBefore(contract.getStartDate()) || dto.claimDate().isAfter(contract.getEndDate()))
    throw new BusinessRuleException("Claim date hors periode");
  Claim claim = new Claim();
  claim.setContract(contract);
  claim.setDescription(dto.description());
  claim.setClaimDate(dto.claimDate());
  claim.setDeclarationDate(LocalDate.now());
  claim.setEstimatedAmount(dto.estimatedAmount());
  claim.setReimbursedAmount(BigDecimal.ZERO);
  claim.setStatus(ClaimStatus.SUBMITTED);
  claim.setClaimNumber("CL-"+Year.now()+"-"+(System.currentTimeMillis()%100000));
  if(file!=null && !file.isEmpty()){
    String unique = UUID.randomUUID()+ext(file);
    Path dest = rootLocation.resolve(unique);
    Files.copy(file.getInputStream(), dest);
    claim.setDocumentPath(dest.toString());
  }
  return ClaimMapper.toDto(claimRepository.save(claim));
}
\end{lstlisting}

\section{Regard critique et limites corrigées partielles}
\textbf{Corrigé depuis rapport initial :} autorisation par rôle désormais effective au niveau HTTP (hasRole/hasAnyRole) + roleGuard frontend. Ce n'était inopérant dans première version mais l'est maintenant sur /api/users.

\textbf{Limites restantes :}
\begin{itemize}
\item Gestion erreurs trop grossière : GlobalExceptionHandler renvoie souvent 400, devrait 404/409/422/403 selon type, format RFC9457 \cite{rfc9457}.
\item Secret JWT en clair dans application.yaml, devrait être variable env.
\item Schéma géré par hibernate ddl-auto:update, pas versionné, pas rollback.
\item JWT peu défensif : pas de claim rôle, 24h long, pas de refresh/revocation, pas de catch TokenExpired dans filtre -> 500 au lieu de 401 propre.
\item Image Docker root, pas de limites, pas de cache Maven, tests skip dans build.
\item Pas de CI, pas de pagination/filtrage listes, README désaligné.
\item Stockage fichier local uploads/ non persistant hors volume, pas de limite taille, pas de validation type MIME.
\end{itemize}

\chapter{Conclusion}
Stage d'un mois chez Vermeg : mini-API REST assurance opérationnelle sur périmètre demandé élargi. Service expose clients avec règles CIN/âge/soft-delete, contrats avec numérotation serveur, sinistres avec validation période + statut ACTIF + upload justificatif, utilisateurs avec rôles ADMIN/AGENT effectifs au niveau HTTP Security et guards Angular. Base PostgreSQL, JWT 24h, validation entrées, règles métier centralisées, documentation OpenAPI interactive, environnement reproductible Docker Compose, client Angular complet.

Sur plan technique, découverte écosystème Spring Boot, JPA, Security, Docker et Angular avec guards. Compréhension architecture couches, DTO, règles centralisées serveur non négociables.

Sur plan critique, travail comporte faiblesses documentées : gestion erreurs uniforme, secret non externalisé, couverture test faible, conteneurisation dev-only, stockage fichier simple. Point positif majeur depuis rapport initial : autorisation par rôle désormais effective, contrairement à première version où annotations @PreAuthorize étaient inopérantes sans @EnableMethodSecurity - défaut corrigé par configuration HTTP Security. Frontend passé de maquette partielle à client complet avec administration employés, prouvant que l'API est consommable.

Ce stage a donné un premier aperçu d'éditeur logiciel financier où correction, traçabilité et lisibilité comptent autant que fonctionnalités visibles - exigence à conserver pour suite cursus.
