\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
Le cycle d'ingénieur en Génie Logiciel de l'ISIMG prévoit, dès la première année, un stage d'initiation d'une durée minimale de quatre semaines. Ce stage a pour objet la découverte de l'organisation réelle d'une entreprise du secteur, la mise en pratique des acquis de la formation et la production d'un document professionnel rendant compte du travail effectué.

J'ai effectué ce stage du 1\textsuperscript{er} au 31 juillet 2026 chez Vermeg, éditeur de solutions logicielles pour les services financiers et l'assurance, sous l'encadrement de Mme Faten Kardous, \emph{Lead Developer} au département Insurance Market Operations.

La gestion d'un portefeuille d'assurance repose sur trois objets liés par une chaîne de dépendances stricte : un \textbf{client} souscrit un ou plusieurs \textbf{contrats}, et un \textbf{sinistre} ne peut être déclaré que sur un contrat en cours de validité. Une application qui se contenterait d'enregistrer ces données sans faire respecter ces dépendances produirait des enregistrements dépourvus de sens juridique. La question posée était donc : \textbf{comment concevoir un service REST qui expose ces trois objets tout en garantissant, côté serveur, que les règles du métier assurantiel ne peuvent être contournées, quel que soit le client appelant ?}

Huit objectifs opérationnels ont été fixés pour la version finale :
\begin{enumerate}[label=\arabic*.,leftmargin=*]
  \item modéliser le domaine client -- contrat -- sinistre -- utilisateur et le persister ;
  \item exposer une API REST complète (17 endpoints finaux) ;
  \item centraliser 14 règles métier dans la couche service ;
  \item protéger les accès par JWT avec rôles ADMIN/AGENT effectifs au niveau HTTP ;
  \item permettre l'upload optionnel de justificatifs de sinistres (multipart) ;
  \item gérer le soft-delete des clients (champ \texttt{active}) ;
  \item publier une documentation OpenAPI exploitable sans lecture du code ;
  \item valider la consommation par un client Angular complet avec guards.
\end{enumerate}

Ce rapport rend compte du travail en cinq chapitres. Le chapitre 1 présente l'entreprise, le cadre et la méthode. Le chapitre 2 formalise le besoin et la conception. Le chapitre 3 détaille la réalisation technique incluant les nouvelles règles. Le chapitre 4 expose la vérification et le regard critique. Le chapitre 5 dresse le bilan.

\begin{lstlisting}[caption={RM5/RM6 + upload fichier -- version finale avec MultipartFile.},label={lst:claim}]
@Transactional
public ClaimResponseDto createClaim(Long contractId, ClaimCreateDto dto, MultipartFile file) {
    Contract contract = contractRepository.findById(contractId)
            .orElseThrow(() -> new NotFoundException("Contract not found"));
    if (contract.getStatus() != ContractStatus.ACTIVE)
        throw new BusinessRuleException("Contract is not ACTIVE");
    if (dto.claimDate().isBefore(contract.getStartDate())
            || dto.claimDate().isAfter(contract.getEndDate()))
        throw new BusinessRuleException("Claim date hors periode");
    Claim claim = new Claim();
    claim.setContract(contract);
    claim.setDescription(dto.description());
    claim.setClaimDate(dto.claimDate());
    claim.setDeclarationDate(LocalDate.now());
    claim.setEstimatedAmount(dto.estimatedAmount());
    claim.setReimbursedAmount(BigDecimal.ZERO);
    claim.setStatus(ClaimStatus.SUBMITTED);
    claim.setClaimNumber("CL-"+Year.now()+"-"+(System.currentTimeMillis()%100000));
    if (file!=null && !file.isEmpty()){
      String unique = UUID.randomUUID()+ext(file);
      Path dest = rootLocation.resolve(unique);
      Files.copy(file.getInputStream(), dest);
      claim.setDocumentPath(dest.toString());
    }
    return ClaimMapper.toDto(claimRepository.save(claim));
}
